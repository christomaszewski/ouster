# CPU loop, telemetry, shared-memory and GPU follow-up

The subsequent [combined configuration comparison](cpu-combined-2026-11-14.md) provides a
clean ten-run comparison against the original unoptimized driver and the current recommendation.
The earlier overlapping combined sequences documented below remain excluded.

This follows the [organized crop study](cpu-crop-gpu-2026-11-13.md). The baseline is its ROS `3bf8744cedeaecfe21fd726898be6eb617229577` / SDK `71b8c20df39141f5ec5154ec8ce9afc69f00ae52`, not the original unoptimized driver. The production candidate keeps the CPU backend, sensor settings, point fields, organized layout and publication cadence. Telemetry throttling, middleware changes and CUDA are measured separately.

## Changes retained in the CPU candidate

- Fuse Cartesian coordinate computation into the final PointCloud2 writer. This removes the full XYZ intermediate and its memory traffic while preserving range masking, float rounding, timestamps, padding, NaNs, density, transforms and cropped column selection.
- Read image channels directly from their native SDK field types, avoiding full integer staging arrays. Preserve the original uint32 SIGNAL and uint16 REFLECTIVITY/NIR intermediate conversions, missing-channel behavior, exposure state and subscriber gating.
- Fuse SDK exposure passes while preserving the intermediate rounding boundary. Public SDK headers and ABI remain unchanged.
- Read only the selected LaserScan ring, with contiguous spans replacing per-point modulo. Preserve the old unsigned-index behavior even for unusual negative shifts and non-power-of-two synthetic widths.
- Add optional `telemetry_max_rate_hz`, default `0.0` (existing per-packet behavior). A positive limit coalesces unchanged telemetry using a steady clock. Changes to any of the four status/countdown fields publish immediately. This is a configuration-time option and does not synthesize messages without incoming packets. Cleanup removes the handler/publisher before node cleanup; reconfiguration tests cover on/off/on and invalid configuration recovery.

The candidate does not change sensor resolution, return profile, image demand, cloud schema, compiler math semantics or executor. It does not migrate to SDK 1.x. All comparisons request all four LEGACY images, so image subscriber gating cannot explain this study's gains.

## Where time remains

A separate diagnostic `perf record` run on the previous crop driver attributed approximately 13.49% of user-cycle samples to cloud packing and 5.18% to Cartesian conversion. ImageProcessor accounted for 10.40%, with additional beam correction, exposure selection/application and output conversion symbols. SDK field unpacking and memcpy also remained material. LaserScan conversion accounted for about 2.12%. These are sampled symbol shares, not guaranteed whole-process savings, and the profiler adds overhead.

For the current combined-node graph, `publish(const Message&)` does not introduce an extra rclcpp ownership copy when intra-process communication is disabled. Replacing it with a unique pointer would not remove serialization or transport copies to other processes. The installed `rmw_zenoh_cpp` 0.10.6 reports message loans unsupported. `PointCloud2::data` is a CPU-backed `rosidl::Buffer`; the ordinary CPU-group publication path still stages serialized CDR before transport shared memory.

The raw PacketMsg publisher also uses buffer-aware dispatch. With no matched raw subscribers, the installed Zenoh path already returns before sizing, allocation or serialization. Queue copies, locks and worker wakeups remain. The diagnostic does not isolate their full cost, but provides no evidence of a large missed serialization cost. Raw subscriber gating is therefore not added speculatively: graph lookups must stay off the UDP thread, and delayed demand updates can lose packets when a recorder joins. Existing bounded raw queues and replay behavior are preserved.

Each benchmark compares the actual old and new implementation against frozen references. CPU benchmarks use CPU 2; power mode MAXN and schedutil remain unchanged. These are processing-stage costs, not complete driver CPU or energy measurements.

Cloud measurements use two opposite-order repeats, nine rounds of 128 frames per case. Image/exposure measurements use two opposite-order repeats, six rounds of 200 frames. The unchanged beam-correction control varies less than 0.51%. LaserScan uses four mirrored cases with eight alternating rounds of 1,000 frames; its absolute delta is only about 0.157 percentage points of one core at 10 Hz. Frozen cloud comparisons cover eight captured sensor frames and all supported layouts/profiles in unit tests; image tests preserve multi-frame exposure behavior. ## Live comparison protocol

All Linux ARM64 images are built on the Mac and copied to the Orin at 10.160.1.21. The real sensor is the OS-0-128 at 10.160.1.51, FW 2.5.3, LEGACY 2048×10. Tests use original 48-byte organized/destaggered clouds, all `IMU|PCL|SCAN|IMG|RAW|TLM` processors, namespace `/cpu_next`, ROS domain 86 and the same Zenoh router with a 256 MiB shared-memory pool. Host network/IPC and unlimited memlock are identical.

Each primary comparison uses A–B–B–A order, approximately 60 seconds of CPU counters after 15 seconds of settling, and approximately 90 seconds of cloud/image observation. **100% CPU means one core.** Driver CPU excludes the supervisor; service CPU includes it. Observer and router are measured separately. No offline GPU benchmark, host compilation or large transfer runs during a live CPU sample.

The final observer uses raw serialized cloud/image callbacks and a lightweight native C++ telemetry counter. The initial Python telemetry observer consumed substantial CPU at approximately 1,280 callbacks/sec. Those pilot results are retained separately and are not pooled with the native-counter comparisons. Sensor alert snapshots are retained independently of host UDP counters: ten clouds/sec and zero host receive errors do not prove every sensor packet arrived.

**Alert-clock correction:** initial analyses incorrectly aligned alert `realtime` with lidar packet timestamps. The [FW 2.5.3 API manual, §2.4.3](https://data.ouster.io/downloads/tcp-http-api-manual/api-manual-v2.5.3.pdf) distinguishes OS system clocks from hardware lidar timestamp clocks. Those timing classifications and packet-clock filters are withdrawn. Alert records/cursors establish presence in a snapshot; continuity-qualified cursor differences identify records first appearing in the later snapshot, without bounding when the events were generated. They cannot place an event inside a CPU interval without a separate system-clock correlation. Original analyses are preserved as superseded evidence. CPU counters, image identities, output-rate and schema checks are unaffected.

### Default CPU loop comparison

The full-width series uses `light_combined_a1_360`, `b1`, `b2`, `a2`; the cropped series uses the corresponding `*_90` labels. Each compares the previous crop driver with the final CPU candidate. Telemetry remains per-packet, and the azimuth/crop choice is identical within each pair.

| --- | ---: | ---: | ---: |
| Full 128×2048, 360° | 51.276% → 50.860% | 0.81% | 64.044% → 63.300% |

The full-driver effect is much smaller than isolated loop speedups. The 0.81% full-width difference is smaller than the baseline trial spread and is **inconclusive as a meaningful full-driver speedup**. The cropped reduction repeats consistently. Driver instructions fall 8.12% full-width and 12.31% cropped; cycles fall 0.80% and 6.31%. All perf events run for their full interval. These are two samples per condition with adaptive clocks, not a confidence interval or a long-duration fleet benchmark.

Independent [full-width](../var/cpu-next-2026-11-13/results/independent-light_combined360-audit.json) and [cropped](../var/cpu-next-2026-11-13/results/independent-light_combined90-audit.json) audits verify all observed clouds/images remain approximately 10 Hz without header gaps above 150 ms, schemas and sensor settings match within each series, and host UDP error deltas are zero. Sensor alert snapshots include transmission and internal-overflow records, but their timing cannot be inferred from packet timestamps. No loss-free claim is made, and the marginal full-width CPU difference is not promoted as a robust speedup.

Mean driver CPU falls **51.038% → 32.190% (36.93%)**, and service CPU **63.237% → 34.151% (46.00%)**. Telemetry falls from 1,280.03 to 9.960 Hz. Clouds and all four images remain approximately 10 Hz with unchanged layouts and no observed header gaps above 150 ms.

This graph includes both the internal health subscriber and an external native telemetry counter. The native counter falls from 17.54% to 0.35% CPU; this is measured separately and excluded from service CPU. The Python cloud/image observer stays at approximately 9.5–9.8%. These results apply to this graph, and are not a promise of the same reduction with a different subscriber graph. The default remains unlimited telemetry, so this gain is not attributed to the default CPU loop changes.

All four trials have zero host UDP error deltas and fully scheduled perf counters. The [independent audit](../var/cpu-next-2026-11-13/results/independent-light-telemetry-audit.json) retains each trial, alert snapshots and observer-load qualifications. Previous claims placing particular alerts inside or outside these CPU intervals relied on the invalid clock mapping and are withdrawn. Both matched pairs support the telemetry reduction; neither is labeled packet-loss-free from these records. The initial Python-observer pilots remain excluded because their subscriber graph differs.

## Experimental direct shared-memory serialization

The isolated middleware experiment uses official rmw_zenoh source `4e17ccfb9e114c87ac87b802e705b60e283b4115` (0.10.6). An opt-in environment variable serializes large CPU-group messages directly into a Zenoh shared-memory allocation. Allocation failure falls back to the original heap path. If actual serialized length differs from the estimated allocation, it falls back to an exact-length owned buffer rather than transmitting trailing bytes.

Both controls use the same rebuilt library and differ only in `OUSTER_EXPERIMENT_CPU_GROUP_SHM=0/1`. Forty exact 12 MiB PointCloud2 frames pass in each local scenario: off, on, exhausted pool and deliberately oversized allocation. All 162 exported symbols match the original build. This is a middleware prototype, not a fleet base update or end-to-end zero copy. Reproduction source is in [tools/rmw_shm_test](../tools/rmw_shm_test/README.md).

The live middleware controls use the same earlier telemetry-capable ROS build with unlimited telemetry, not the final loop-optimized CPU build. The experiment library is SHA-256 `30f1ea71d8349d84177571dd221b417aad13b1457166d8b585409384ca0231f0` in both images. Its effect is measured within that pair; reductions from separate CPU, telemetry, middleware and GPU series must not be added together.

The fresh `light_rmw_a1`, `b1`, `b2`, `a2` series reduces driver CPU **52.380% → 49.710% (5.10%)** and service CPU **64.963% → 62.131% (4.36%)**. Instructions fall 3.19%, cache references 5.38%, and cache misses 16.57%; these aggregate counters do not establish a particular DRAM-bandwidth reduction. Both candidate measurements agree closely. Clouds/images retain their schemas and approximately 10 Hz rates; unlimited telemetry stays approximately 1,280 Hz.

The [live audit](../var/cpu-next-2026-11-13/results/independent-light_rmw-audit.json) verifies configuration, source, runtime toggle, stream continuity and zero host UDP errors. Sensor transmission alerts are present in the retained history; the snapshots do not establish their timing within a CPU interval or packet completeness. The result supports further middleware integration work, while the current production fleet middleware stays unchanged.

A separate, untimed `gpu_rmw_api_debug_smoke` confirms the actual allocation path with live GPU clouds. A Mac-built diagnostic preload calls `rmw_set_log_severity(RMW_LOG_SEVERITY_DEBUG)` in the driver process; ROS log-level arguments alone do not enable this middleware's private logger. The tested middleware binary and runtime image remain unchanged. The log records **358 cloud allocations of 12,583,181 serialized bytes and 1,400 image allocations of 524,344 bytes**, with no exact-length heap fallback. The observer receives 350 clouds and 349 frames per image topic at approximately 10 Hz, with no header gaps above 150 ms. Its maximum cloud arrival gap is 395 ms, so header continuity does not imply evenly paced delivery. GPU validation matches eight complete same-scan CPU clouds and uses one output binding across 442 processed frames. Allocation counts and observer counts cover different lifetimes; they are not a one-to-one delivery assertion. Debug logging/shim CPU is excluded from every performance comparison, and this trace does not retroactively prove the allocation branch for every message in earlier timed trials. [Independent allocation/lifecycle audit](../var/cpu-next-2026-11-13/results/independent-gpu-rmw-api-debug-audit.md).

## GPU improvements and limits

The useful improvement is buffer ownership: register the ordinary final CPU-owned cloud once and let CUDA write it directly. The live prototype still copies the native input fields into persistent pinned input storage each frame; those **9 bytes per input pixel plus timestamps are charged**. It completes CUDA before ROS publication and releases registrations before output replacement or destruction. Generic callbacks default to CPU unless the caller explicitly promises immutable output access; a callback that may mutate it must not make that promise. The combined driver's synchronous read-only publication callback satisfies the contract.

The backend supports single-return LEGACY, original organized/destaggered 48-byte points, all rows, no input mask, and full/cropped output. It is dynamically loaded and opt-in; the default requires no CUDA dependency. Strict experiment mode rejects fallback. Fake-backend retention/reallocation/lifecycle tests and exact native-type real/synthetic CUDA comparisons protect ownership and field semantics.

| Native-input standalone GPU mode | Full wall / CPU ms | 637-column wall / CPU ms |
| --- | ---: | ---: |
| Register output only; input copy charged, burst | 0.931 / 0.290 | 0.485 / 0.274 |
| Register inputs and output persistently, burst | 0.527 / 0.029 | 0.225 / 0.028 |

Persistent registration of all input fields is a separate ownership experiment; the live driver does not yet guarantee that scan-ring contract. Earlier widened-field fixtures likewise must not be described as direct attachment to the native SDK arrays.

Ten-Hz per-frame traces reveal a serious idle-resume effect: the first GPU call after several seconds of CPU-only work takes approximately 134–145 ms. All sixteen standalone deadline misses occur at this boundary, with negligible start lateness. After those cold calls, output-only median wall/CPU times are 1.749/0.463 ms full and 1.385/0.477 ms cropped. Median round-average timings including cold calls are 5.96/2.59 ms and 5.58/2.58 ms. Warm burst numbers therefore do not establish a cold-start latency guarantee.

SoA lookup tables, alternative block sizes, shared-memory tiling and CUDA graphs did not improve the original mapped path enough to retain. Per-frame memory registration is expensive. The same native backend passes all eight real-frame checks inside the ROS runtime using NVIDIA container injection, without changing the host CUDA installation or power policy.

The source, build scripts and traced benchmark are retained in [tools/gpu_cloud_test](../tools/gpu_cloud_test/README.md). GPU processing does not remove packet decoding, image work, middleware serialization or downstream copies. The complete-driver comparisons below measure its benefit; competing workloads, power consumption and longer-duration latency qualification remain outside their scope.

## Combined experiment and disposition

The combined image `ouster_driver:cpu-next-gpu-rmw`, ID `sha256:38639ba36ee6661687b9c37ebe29775dd1a5a5de70aacc6f5fb4d315bac03fd2`, inherits the exact tested GPU image and replaces only the middleware library. Its 15 overlay libraries and middleware pass eager loading; source, library hashes, inherited layers and runtime configuration are verified in [build evidence](../var/cpu-next-2026-11-13/gpu-rmw-build/summary.json). GPU and middleware remain disabled unless explicitly requested.

The first combined series, `light_gpu_rmw10_a1`, `b1`, `b2`, `a2`, holds telemetry at 10 Hz and compares CPU/ordinary serialization against GPU/direct shared-memory serialization. **Its performance result is inconclusive and excluded.** Camera test containers started during B1 and remained present through B2/A2. The CPU control changed from 30.70% to 23.65% while its instruction count stayed similar and CPU frequencies changed substantially. There is no complete uncontaminated A/B pair. The external workloads were left untouched. [Concurrency evidence](../var/cpu-next-2026-11-13/results/combined-concurrency-limitation.json), [independent pilot audit](../var/cpu-next-2026-11-13/results/independent-light_gpu_rmw10-pilot-audit.md).

A fresh `light_gpu_rmw10_repeat_*` series began after those camera containers were removed. Its closing CPU control was also contaminated: another camera container started at 04:31:47 UTC during A2's 04:31:46–04:32:46 CPU interval, then ran package installation and parallel compilation. A bounded event replay plus a continuous event stream records this overlap. The provisional 18.63% driver / 17.46% service mean reductions are **withdrawn and must not be used**. A1/B1/B2 precede the observed external container activity, but they do not supply the closing control needed for the planned comparison. Neither repeated combined series establishes a combined deployment gain. The [independent repeat audit](../var/cpu-next-2026-11-13/results/independent-light_gpu_rmw10_repeat-audit.md) passes 259 operational/configuration checks while withholding aggregate performance claims. A separate [topic-set check](../var/cpu-next-2026-11-13/results/independent-fresh-series-image-topic-check.json) confirms all four expected images in all 24 earlier primary trials.

The retained production changes are the validated CPU loops and optional telemetry limiter, with unlimited telemetry still the default. CUDA and middleware changes remain separate experiments. The isolated GPU result is useful, but the idle-resume latency and narrow supported layout prevent treating it as a general production replacement. Percentages from the separate comparisons must not be added together.

## Final state
